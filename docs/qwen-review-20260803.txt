Я внимательно проанализировал код репозитория `tormoz70/little-big-files`. Проект представляет собой интересную архитектуру (content-addressed storage, шардирование, deduplication), но в нем есть несколько **критических багов**, связанных с надежностью (reliability), обработкой паник (crash recovery) и управлением памятью.

Ниже приведен подробный разбор найденных проблем с указанием файлов и способов их исправления.

### 1. Критическая потеря данных при восстановлении журнала (Crash Recovery Bug)
**Файл:** `internal/recovery/journal.go`
**Функция:** `ReadJournal`

**Суть бага:**
Журнал ингейста (`ingest_journal.ndjson`) пишется построчно. Если система упадет (crash/panic) или потеряет питание в момент вызова `Append` (между записью JSON-строки и записью символа `\n`), последняя строка в файле окажется "обрезанной" (невалидный JSON или отсутствует перенос строки).

При запуске `ReadJournal` используется `bufio.Scanner`, который успешно прочитает эту "обрезанную" строку до EOF. Затем `json.Unmarshal` вернет ошибку, и функция **немедленно прервется, вернув `error`**.

**Последствия:**
Все валидные записи журнала, которые были успешно прочитаны до поврежденной строки, **отбрасываются**. Инструмент восстановления (recovery tool) завершится с ошибкой, и система не сможет восстановить корректное состояние, даже если 99.9% журнала целы. Надежный WAL/Journal reader обязан игнорировать последнюю "битую" строку (так как транзакция для нее все равно не успела закоммититься в БД).

**Как исправить:**
```go
for sc.Scan() {
    line := sc.Bytes()
    if len(line) == 0 { continue }
    var e JournalEntry
    if err := json.Unmarshal(line, &e); err != nil {
        // ВНИМАНИЕ: Если это последняя строка и EOF, нужно просто прервать цикл (ignore partial write),
        // а не возвращать ошибку, которая обнулит весь out!
        slog.Warn("ignoring partial journal entry", "err", err)
        break 
    }
    out = append(out, e)
}
return out, sc.Err() // sc.Err() вернет ошибку только если были проблемы чтения самого файла
```

### 2. Дедлок HTTP-сервера при панике батча записи
**Файл:** `internal/storage/write_buffer.go`
**Функция:** `WriteBuffer.Flush`

**Суть бага:**
Функция `Flush()` забирает батч из `wb.pending` и вызывает `wb.sm.batchAppend(batch)`. После этого она проходит по циклу и рассылает результаты в каналы `pw.done`:
```go
wb.sm.batchAppend(batch)
for _, pw := range batch {
    pw.done <- pw.err // Сигналим ожидающим горутинам
}
```
Если внутри `batchAppend` (или глубже в `appendLocked`) произойдет **паника** (например, из-за corrupted memory, nil pointer или специфичной ошибки I/O), выполнение `Flush` прервется. Цикл рассылки `pw.done` **никогда не выполнится**.

**Последствия:**
Все HTTP-хендлеры, которые в данный момент ждут результата записи в `wb.Append()` на строке `case err := <-pw.done:`, **зависнут навсегда (goroutine leak)**. Это гарантированно приведет к исчерпанию лимитов соединений и полному зависанию API.
В `Flush` (или внутри самого `batchAppend`) обязательно должен быть `defer recover()`, который в случае паники пройдет по `batch` и отправит ошибку во все `pw.done`.

### 3. "Зависание" пакетов и смерть воркеров при панике
**Файл:** `internal/ingestion/unpack_worker.go`
**Функция:** `UnpackQueue.worker`

**Суть бага:**
```go
case pkgID := <-q.ch:
    if err := q.svc.UnpackLargePackage(ctx, pkgID); err != nil { ... }
    q.mu.Lock()
    delete(q.inflight, pkgID) // Очистка флага "в работе"
    q.mu.Unlock()
```
Если `UnpackLargePackage` (например, при парсинге сложного ZIP-архива) упадет с паникой, горутина воркера умрет (сработает только `defer q.wg.Done()`).
Строка `delete(q.inflight, pkgID)` **никогда не выполнится**.

**Последствия:**
1. **Вечный инфлайт:** `packageID` навсегда останется в карте `inflight`. Периодический `recoverPending` скан проверяет этот флаг и пропускает пакеты, которые уже "в работе". В итоге этот пакет **никогда больше не будет перепакован**.
2. **Утечка воркеров:** Пул воркеров не восстанавливается после паник. Если произойдет 10 паник на разных "битых" архивах, все воркеты умрут, и очередь распаковки (UnpackQueue) полностью остановится.
Необходимо добавить `defer func() { recover(); delete(...) }()` внутри обработки `case pkgID`.

### 4. OOM / Утечка памяти при старте (Memory Spike on Startup)
**Файл:** `internal/storage/segment.go`
**Функция:** `SegmentManager.openSegmentFile`

**Суть бага:**
При старте приложения (или после краша) менеджер сегментов читает активный сегмент, чтобы проверить его целостность (найти валидный "хвост" через `truncateToValid`):
```go
data, err := os.ReadFile(path) // Читает ВЕСЬ файл в RAM!
```
**Последствия:**
Проект позиционируется как "little-big-files" для high-volume ингейста с шардированием по объему. Размер одного сегмента (`maxSegmentSize`) может достигать сотен мегабайт или нескольких гигабайт. При каждом рестарте пода приложение будет аллоцировать **гигабайты оперативной памяти** просто для валидации последних записей. Это может привести к OOMKilled на старте в средах с ограниченной памятью (например, в Kubernetes).
Для валидации "хвоста" достаточно читать файл с конца (seek с конца) или использовать `io.Reader` с буфером, а не загружать весь сегмент в `[]byte`.

### 5. Блокировка Control Plane (Holding Mutex across Network Calls)
**Файл:** `internal/coordinator/registry.go`
**Функция:** `Registry.PatchShardState`

**Суть бага:**
Функция изменения состояния шарды берет глобальный мьютекс координатора:
```go
reg.rotationMu.Lock()
defer reg.rotationMu.Unlock()
```
И, удерживая его, делает синхронные HTTP-запросы к шардам:
```go
if _, err := reg.FetchStats(ctx, target.PrimaryURL); err != nil { ... }
total, sealedAt, err := reg.sealShardRemote(ctx, active, "manual_promote")
```
**Последствия:**
Если сеть "лагает" или шарда "отвалилась", HTTP-клиент будет ждать таймаута (в `NewRegistry` указан `Timeout: 60 * time.Second`). Все эти 60 секунд `rotationMu` заблокирован.
В это время **ни одна другая операция управления кластером** (например, автоматический `SealAndRotate` или регистрация новых шард, если они зависят от этого лока) не сможет выполниться. Control plane координатора полностью парализуется из-за медленной сети. Сетевые вызовы нужно выносить за пределы критической секции.

### 6. HTTP Header Injection / Битый `Content-Disposition`
**Файл:** `internal/api/handlers.go`
**Функция:** `Server.serveFile`

**Суть бага:**
При скачивании файла заголовок формируется через простой `Sprintf`:
```go
w.Header().Set("Content-Disposition", fmt.Sprintf(`attachment; filename="%s"`, filename))
```
Поле `filename` берется из `file.OriginalFilename`, которое задается клиентом при загрузке (user input).
**Последствия:**
Если злоумышленник или легитимный пользователь загрузит файл, содержащий двойные кавычки (`"`) или CRLF (`\r\n`), это приведет к:
1. Нарушению RFC 6266 (браузер обрежет имя файла на второй кавычке или упадет).
2. В старых версиях HTTP-стеков или прокси-серверов это может привести к HTTP Response Splitting (инъекции заголовков).
**Как исправить:** Использовать `mime.FormatMediaType("attachment", map[string]string{"filename": filename})` — эта функция из стандартной библиотеки корректно экранирует кавычки и UTF-8 символы.

### 7. Потенциальная Zip Bomb (OOM в воркерах)
**Файл:** `internal/ingestion/unpack_large.go`
**Функция:** `UnpackZip`

Хотя исходный код `UnpackZip` не был полностью выгружен, судя по сигнатуре `members, unpackErr := UnpackZip(zipBytes)` и тому, что результаты (члены ZIP-архива) затем передаются в `persistZipMembers` для записи в BlobStore, существует риск **Zip Bomb**.
Если система принимает ZIP-архивы от внешних поставщиков (suppliers), и `UnpackZip` распаковывает все файлы **в оперативную память** (в слайс структур с `[]byte`), то один "битый" или злонамеренный ZIP-архив размером 50 МБ, содержащий внутри 10 ГБ XML-файлов, гарантированно "уронит" (OOM) процесс воркера. В таких системах распаковка должна вестись потоково (streaming) или с жестким лимитом на суммарный `unpacked size`.

### Резюме:
Код написан на хорошем уровне с точки зрения архитектуры (правильный use of append-only segments, deduplication через Bloom filter, транзакционность), но в нем **не хватает defensive programming при работе с паниками и I/O ошибками**. Исправление багов в `journal.go`, `write_buffer.go` и `unpack_worker.go` критически необходимо перед тем, как запускать это в Production под реальной нагрузкой.
